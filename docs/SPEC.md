# Козацький хутір (Cossack Kin) — SPEC v1.3

> Атмосферна піксельна idle-гра для мобільних (Android → iOS). Гравець відроджує козацьке поселення — укріплену Січ і хутори навколо неї, — будує господарство, водить військо в походи, розвиває культуру й веде рід шляхом Війська Запорозького з краю в край.
> **v1.1 (2026-11-16):** внесено рішення з `docs/SPEC-REVIEW.md` — роздільність 320–400 px, устрій «хутір + передмістя + Січ» (§3.0), нові краї в історичному порядку (§3.7), аналітичний `advance()` (§3.8), арт і музика повністю кодом (§5, §7, ADR 004–005), етап M-ART (§14).
> **v1.2 (2026-11-19):** календар відкриттів (§2.4), сюжетні віхи країв (§2.5), детерміноване різноманіття — вісті, мандрівники, товар дня, погода в економіці (§2.6); метрики новизни в `pnpm balance` (§2.3, §12.3); ADR 009. Відповіді власника: v1 ≈ 3–4 міс., герої Сотник і Військовий писар.
> **v1.3 (2026-11-19):** монетизація = rewarded-реклама за вибором + магазин (писанки як єдина преміум-валюта, «Без реклами», «Козацька казна», косметика, зручність; §4), постійні завдання — ланцюжок, щоденні, тижневі, повторювані (§3.10), профілі симулятора free / ads / payer (§2.3, §12.3), `StoreService` (§9.4); ADR 010 частково замінює ADR 006.

## 0. Інструкції для Claude Code

1. Працюй **по етапах** із розділу 14. Не починай наступний етап, поки поточний не відповідає своїм критеріям приймання.
2. `src/core` — це **чистий TypeScript** без DOM, Pixi, React чи Capacitor. Уся економіка детермінована й покрита тестами.
3. Усі числа балансу живуть у `src/content/*.ts`. У логіці магічних чисел немає.
4. Після кожної зміни балансу запускай `pnpm balance` (розділ 12.3) і вкладай звіт у PR.
5. Тексти тільки через i18n-ключі. Мова за замовчуванням `uk`, друга `en`.
6. Перед комітом мають проходити `pnpm typecheck && pnpm test && pnpm lint`.
7. Візуальні зміни перевіряй скриншотами Playwright у мобільному в'юпорті 390×844 (день + ніч) і `/art-review`. Еталон стилю — `docs/art/ART-BIBLE.md`.
8. Графіка — головний пріоритет проєкту. Спрайт або ефект, який не пройшов `art-director`, не вважається готовим.

### Стовпи дизайну
1. **Атмосфера, затишок і життя.** Селище — це діорама, на яку приємно дивитися о будь-якій порі доби й у будь-яку погоду. Кожна покупка змінюється візуально.
2. **Повага до часу гравця.** Офлайн-прогрес, ліміт накопичення, який заохочує 1–2 заходи на день, і жодних штрафів за пропуск.
3. **Чесна монетизація.** Реклама й покупки тільки допомагають і прикрашають. Без них гру можна повністю пройти, хоч і повільніше; увесь контент безкоштовний (§4).
4. **Різноманіття через краї.** Кожне селище має власний пейзаж, будівлі, музику **і унікальну механіку**, а не лише інші числа.
5. **Культурна автентичність.** Ремесла, звичаї, пісні й свята показані з любов'ю і без стереотипів.

## 2. Ігровий цикл

### 2.1 Мікроцикл (одна сесія, 5–10 хв)
1. Відкрити гру і побачити вікно «Поки тебе не було…» з накопиченим доходом. Можна подвоїти за рекламу.
2. Забрати здобич із походів і відправити козаків у нові.
3. Витратити дукати на будівлі (кілька покупок «MAX»).
4. Витратити славу на будівлі Січі, культуру і героїв.
5. Виконати 1–3 щоденні завдання і забрати щоденну нагороду.
6. За бажанням запустити «Ярмарковий день» (×2 доходу на 30 хв) за рекламу.
7. Вийти. Гра нагадає локальним сповіщенням, коли повернуться козаки або заповниться комора.

### 2.2 Макроцикл (дні й тижні)
- Прокачати селище до **Розквіту** (розділ 3.6), переселитися в новий край, отримати **Клейноди** і вкласти їх у **Родове дерево**.
- Краї йдуть **історичним шляхом Війська Запорозького** — від Хортиці 1550-х до Нової Січі (§3.7). Переселення — це перехід роду в наступну добу.
- Завершені селища стають «Землями роду» і платять пасивну **данину** (§3.6), тож туди хочеться повертатися подивитися.

### 2.4 Календар відкриттів
**Новинка** — те, що гравець помічає як «щось нове»: відчутна покупка (§12.3), сюжетна віха (§2.5), крок «Наказу кошового» (§3.10; справи — ні, M2 Q6), крок унікальної механіки, відкриття системи (перший найм, похід, реліквія, герой, гілка культури, вузол Родового дерева, мета-функція), новий край. Принцип: тиждень 1 — новинка щосесії; далі — щодня; ранні краї короткі й щільні, пізні довші, але з більшими новинками (нова система замість нового рівня).

Сесії S1…S14 — ритм бота §12.3 (2 сесії на день по 7 хв). Віхи M2 вимірюються з M2-27 у вікнах рядків їхніх тригерів: «Берег Дніпра» S1, «Гонець з городка» S1–S3, «Рада на майдані» S3–S5 (= Майдан 10), «Освячення Покрови» S6–S9 (= церква). Вікна — ціль для `balance-sim`, не жорсткий сценарій: **порядок** — дизайн, **час** — результат балансу. Мітка етапу показує, коли запис узагалі з'являється в грі; **жирні** записи вимірюються вже в M1.

### 2.5 Сюжетні віхи країв
Короткі історичні сценки: заголовок + 1–3 речення + портрет (гонець, кошовий, кобзар…) у модальному вікні або підписі над сценою. Дешево: текст + наявні спрайти, без нового арту. Тон §16: дати «близько», без трагічних подій як ігрових, ворог абстрактний.

- **Дані:** `src/content/story.ts`, запис:
  ```ts
  interface StoryBeat {
    id: StoryBeatId;                  // 'khortytsia.messenger'
    land: VillageId;
    trigger: StoryTrigger;            // монотонна умова: перевіряється після advance/дії, тож спрацьовує й офлайн
    portrait: PortraitId;             // 'messenger' | 'otaman' | 'kobzar' | …
    reward: StoryReward | null;       // { kind: 'incomeMinutes' | 'gloryMinutes'; minutes } | { kind: 'pysanky'; n } | { kind: 'unlock'; hero | branch }
    titleKey: string; textKey: string; // story.<land>.<beat>.title|text
  }
  type StoryTrigger = { kind: 'start' } | { kind: 'building' | 'sich'; id; level } | { kind: 'hired'; count }
    | { kind: 'storms'; count } | { kind: 'mechanicStep'; step } | { kind: 'raidsWon'; count } | { kind: 'bloom' };
  ```
- **Стан:** `story: { seen: StoryBeatId[] }`. Нагорода — у момент спрацювання (ядро), модалка — косметика; подія `StoryBeatReached { id, granted }`. Модалки чекають у черзі UI (по одній, після вікна повернення) і не зберігаються: якщо гру закрито до показу, віха лишається побаченою й оплаченою, а модалка вже не з'явиться (M2-25). Нагорода в «хвилинах доходу/слави» не залежить від масштабу краю; поріг-мінімум у контенті.
- Віхи, що посилаються на ще не збудовані системи (похід, герой), додаються разом із цими системами.
- **Міграція v1 → v2 (M2):** віхи, чиї тригери вже виконані, позначаються `seen` мовчки — без модалок і без нагороди (власник, 2026-11-19).
- Нагороди віх моделює `balance-sim` з M2 (§12.3).

|---|---|

## 3. Системи

### 3.0 Устрій селища: хутір, передмістя і Січ
Історично Січ була військовою фортецею: курені навколо майдану, церква, пушкарня, скарбниця, вали й частокіл. Жінки й господарство туди не допускались. Хліб, мед, рибу й худобу давали **зимівники та хутори паланок** навколо, а торгівля й ремесла жили в **передмісті** під брамою. Гра повторює цей устрій: **одне неперервне селище з трьома зонами** (край 1 — 1920 px ≈ 4–5 ширин екрана, камера тягнеться; ADR 011):

```
 ХУТІР 0–768 (господарство)          │ ПЕРЕДМІСТЯ 768–1152 │ СІЧ 1152–1920 (фортеця на кручі)
 за ним Дніпро з човнами (кладка),   │ кузня, шинок,       │ рів, вал, частокіл, брама, вежі,
 верби; поле, город, пасіка, вітряк, │ ярмарок, крамниця,  │ курені довкола майдану, церква,
 хата гончаря, хати; селяни          │ криниця, курган;    │ скарбниця, сторожова вежа,
                                     │ усі змішуються      │ отаман, козаки, вартові
```
Дніпро тече за хутором і передмістям і закінчується рваним берегом перед Січчю. Під горизонтом кожна зона внизу переходить у сухий степ (ART-BIBLE §5). Діти й худоба — M9 (Q12 плану M2); пушкарня у краї 1 прихована (§3.2.1).
- **Хутір і передмістя** — 8 господарських будівель (§3.2), дають **дукати**. Тут живуть селяни.
- **Січ** — 7 військових будівель (§3.2.1), купуються за **славу** і посилюють військо. Тут живуть козаки та кошовий **отаман** (видимий персонаж на майдані з булавою).
- **Зв'язок зон (два взаємні потоки, обидва аналітичні):**
  - **Хутір → Січ: «Харч».** Похідна величина, не валюта: `kharch = Σ(foodLevel_i × kharchPerLevel_i)` з поля, городу, пасіки, вітряка. Вона задає **ліміт козаків** (`maxCossacks = floor(kharch / kharchPerCossack)`). Візуально селяни возять вози з харчем до брами (M2-20: до 3 возів, період = clamp(7500 / харч, 50, 240) с, `CART_PERIOD`; без харчу — жодного).
  - **Січ → хутір: «Оборона».** Сумарний рівень Січі дає +% до доходу хутора («спокій на хуторах»). Походи приносять дукати й реліквії в скарбницю.
- **Чому одне селище, а не дві окремі гри:** обидві зони завжди видно в одній діорамі, а рішення «куди вкласти» постійне й просте. Окремі валюти (дукати / слава) уже розводять дві гілки розвитку, тож третя валюта не потрібна.
- **Автентичні деталі поведінки:** селяни заходять лише до брами й передмістя; козаки ходять у передмістя (шинок, кузня, ярмарок), на свята (Покрова, Купала) спускаються до хутора, де разом танцюють гопак на майдані чи біля вогнищ.
- Таби: **Хутір** (господарство; передмістя — теж тут), **Січ** (будівлі Січі, військо, походи), **Культура**, **Край**, **Ще** (у M2 — Хутір / Січ / Ще; Культура — M4, Край — M5).

### 3.2 Будівлі
- У кожному селищі **8 господарських будівель** (хутір + передмістя) на фіксованих ділянках (plot) мапи і **7 будівель Січі** (§3.2.1).
- Рівні від 0 до **100**.
- **Вартість:** `cost(l) = base × village.scale × growth^l × costMods`, де `growth` ∈ [1.10, 1.30] залежно від будівлі (тест контенту; у краї 1 — 1.10–1.20). Купівля n рівнів — геометрична сума; MAX — замкнена формула через `log10` з корекцією ±1; ×10/×25 купують рівно n (або залишок до стелі), інакше кнопка вимкнена.
- **Дохід:** `prod(l) = baseProd × village.scale × l × milestoneMult(l) × prodMods`
- **Віхи:** рівні 10, 25, 50, 75, 100. На кожній дохід ×2, на 100 — ×3. Кожна віха — це ще й **новий візуальний тір** будівлі (розділ 6.5).
- Режими купівлі: ×1 / ×10 / ×25 / MAX.
- Одна будівля передмістя має тег `army` і дає +силу війська (кузня, ковальня, гарматня).
- Будівлі з тегом `food` дають харч (§3.0).
- У будівлі може бути **робітник**: селяни фізично ходять туди працювати (розділ 6.6).

### 3.3 Тап по селищу
- Тап по порожньому місці дає `max(scale, incomeBase × 0.3)` дукатів, монетки й плаваюче число.
- Тап по будівлі відкриває bottom sheet (щонайменше половину) на рядку цієї будівлі з інформацією і кнопкою покращення; такий тап не заробляє (M2-13).

### 3.4 Військо
- **Загони:**
  - **Козаки-піхота** доступні з самого початку.
  - **Гармаші** відкриваються в краї 5 (Чортомлицька Січ, пушкарня).
  - **Кіннота** відкривається в краї 6 (Слобожанщина, стайні).
- Ціна найму (у дукатах): `unitBase × scale × 1.13^count × mods`.
- **Ліміт:** загальна кількість загонів ≤ `maxCossacks` (харч із хутора + бонус Куренів, §3.0). Коли ліміт досягнуто, кнопка найму показує, що треба більше харчу.
- **Сила війська:** `ArmyPower = Σ(unitPower × count) × (1 + armyBuildingBonus + sichBonus) × heroMods × cultureMods`
- **Пасивна слава:** `glory/s = ArmyPower × 0.02 × mods`
- **Що вже є в M1** (Q1 плану M1: без слави Січ не купити; `src/core/systems/army.ts`, числа `ARMY` у `src/content/economy.ts`):
  | Що | Як у коді |
  |---|---|
  | Загони | лише піхота (`army.infantry`); спільний перемикач ×1/×10/×25/Макс діє й на найм (M2-14, `hireCount`): ×N — рівно N, або залишок до ліміту харчу, якщо його вистачає грошима; Макс — скільки по кишені в межах ліміту |
  | Ціна | `50 × scale × 1.13^n × costMult` (n = уже найнято) |
  | Ліміт | `infantry + n ≤ maxCossacks`; інакше відмова `kharch` (навіть із грошима), без грошей — `ducats` |
  | Сила | `ArmyPower = infantry × 1 × powerMult`; `powerMult = 1 + 3 %·кузня + 2 %·майдан (+ 3 %·пушкарня)` |
  | Слава | `glory/s = ArmyPower × 0.02 × gloryMult`; `gloryMult = 1 + 1 %·шинок + 2 %·церква` |
  | Комора слави | лише офлайн: слава за відсутність ≤ `gloryRate × gloryCapSec`, `gloryCapSec = 4 год + 600 с × скарбниця` |
  Походи й реліквії — M3 (модель нижче); гармаші й кіннота — M10+.
- **Походи:**
  - Одночасно доступні **2 слоти** походів, третій купується писанками.
  - Кожен похід має регіон на мапі, тривалість, рекомендовану силу `P` і таблицю здобичі.
  - `successChance = clamp(ArmyPower / P, 0.35, 1.0)` — це **ймовірність**. Кидок робиться **один раз на старті** seeded RNG, результат зберігається в стані й показується при поверненні (захист від save-scum).
  - Невдача дає 30% здобичі й ніколи не дає нуля.
  - Похід можна почати, лише якщо `ArmyPower ≥ 0.5 × P`. Здобич `k` залежить від тиру походу, тож найважчий похід не вигідний слабкому війську.
  - Тривалості: 5 хв, 30 хв, 1 год, 4 год, 8 год.
  - Здобич: дукати (`incomeBase × k`), слава, шанс на писанки, шанс на **реліквію**.
  - За рекламу **залишок** часу походу скорочується на 50% (максимум 2 рази на похід), а здобич подвоюється (1 раз).
  - Візуально загін під корогвою виходить з брами Січі на чолі з отаманом і повертається зі скринею (§6.6).
- **Модель походів M3** (план `docs/plans/2026-11-23-m3-army.md`, рішення власника 2026-11-24 Q1–Q15; ADR 012):
  | Що | Як |
  |---|---|
  | Армія | похід бере **знімок** `ArmyPower` на старті; військо лишається вдома в економіці (пасивна слава, сила другого слота не змінюються, Q1); візуально йде лише загін (§6.6). Втрат немає (Q2) |
  | Слот | дискримінований union `idle` \| `running { raid }` \| `returned { raid }`; масив фіксованої довжини `RAIDS.maxSlots` (3), відкриті — похідна (`openSlots` = 2 у M3; +1 — Чайки M4, Родове дерево M5, писанки M8b); закритий слот завжди `idle` |
  | Кидок | `startRaid { slot, tier }` кидає **все один раз на старті** з `state.rng`: успіх, писанки, реліквію; здобич у Big рахується тоді ж за сталим доходом (`steadyModifiers`, без вітру моменту, Q4) і зберігається в `RaidRoll`. Що показано на картці перед стартом, те й прийде; покупки під час походу здобичі не змінюють |
  | Формули (числа — `content/raids.ts`) | старт лише при `power ≥ 0.5 × P`; `chance = clamp(power / P, 0.35, 1)`; дукати = `farmIncomeRate(steady) × lootSec[tier] × lootMult`, слава = `gloryRate(steady) × gloryLootSec[tier] × lootMult` (мінімум `REWARD.minPerMinute`); невдача × `failShare` 0.3, ніколи 0; `lootMult` = 1 + скарбниця × `lootPerLevel` + реліквії + чутка; `raidTimeMult` = 1 у M3 (Характерник — M4). Тири відкриває лише сила (Q15) |
  | Писанки (Q6) | малий шанс 1–2 лише на походах ≥ 1 год; накопичуються (стоки — M8b) |
  | Реліквії (Q5) | у M3 — «Пернач» (+5 % сили), «Порохівниця» (+10 % здобичі); «Кобза діда» — у M4 з культурою. Кидок лише серед незнайдених (дублікатів нема); усі знайдені → шанс реліквії стає шансом писанки. **Запобіжник:** лічильник `raids.pity` (успішні кидки тиру ≥ 30 хв без реліквії) — на `pityThreshold(знайдено)`-му успіху реліквія гарантована (`RELICS.pityAt` = [4, 6]: 4 для першої, далі 6 для кожної, Q16); невдача лічильник не рухає. Знайдена реліквія — назавжди (переходить через переселення, §3.6), ефект лише через `collectModifiers` |
  | Час | `returnAt` — абсолютна мітка; `advance` має точку розриву на `returnAt` → `running → returned` + подія `RaidReturned` (ставки не змінюються); `applyOffline` завершує походи до **реального** `now`, не до офлайн-ліміту (§3.8) |
  | Збір (Q9) | вручну: `claimRaid { slot }` → валюти, `relics`, `stats`; слот зайнятий до збору; повернений похід чекає без кінця, здобич не псується. Авто-збір — сток M8b |
  | День | дошка дня (§2.6), день = `dayAt(maxSeen, tzOffsetMin)` (§3.9) |
- **Як подаємо (найкращі практики жанру, план M3 §0.1):** картка показує до старту точні числа — шанс %, здобич успіху й невдачі, шанс реліквії, «ще N сили до певного успіху», а коли запобіжник гарантує реліквію при успіху — «Старі козаки кажуть: реліквія близько»; результат прихований до «Забрати» (UI-селектор у дорозі не має `success`); у дорозі — відлік двома одиницями + «повернуться о HH:MM» + смужка дороги; скриня: коротка тряска → предмети по одному, тап — одразу все, «менше руху» — готовий список; «Ще раз» (той самий тир на дошці дня одним тапом); порожній слот не «пече» червоною крапкою (лише повернений); тир 8 год підписано «на ніч». Не робимо: таймерів, що згоряють, втрат загону, «відновлення» за рекламу, відліку до скидання дошки.
- **Вирішено власником 2026-11-24 (план M3 Q16–Q21 = рекомендації):** запобіжник для кожної реліквії, не лише першої (Q16); «Забрати все» (Q17); групування й час сповіщень M6 (Q18); перший похід гарантовано успішний через P тиру 5 хв (Q19); стеля `s1Actions` (Q20); шанс реліквії як точний % (Q21).
- **Не в M3:** реклама за прискорення/×2 (M8a), 3-й слот, «Завершити похід зараз», авто-збір (M8b), сповіщення (M6; у M3 — чистий `raidAlerts` і mock `NotificationService`), герої й культура для походів (M4), морські походи (край 3).
- **Реліквії:** колекційні предмети з пасивними бонусами, наприклад «Пернач» (+5% сили), «Порохівниця» (+10% здобичі), «Кобза діда» (−5% ціни культури). Колекція — у «Ще → Скарбниця» (знайдені + силуети незнайдених з натяком, де шукати; Q10); на вкладці «Січ» — значки знайдених біля сили війська.

### 3.6 Переселення (престиж)
- **Розквіт селища** настає, коли виконано всі три умови:
  1. усі господарські будівлі мають рівень ≥ 50;
  2. усі відкриті будівлі Січі мають рівень ≥ 25;
  3. виконано **унікальну ціль краю** (див. таблицю 3.7).
- Після Розквіту відкривається кнопка «Переселитися». Гравець може лишитися й докачувати селище до 100, бо Клейнодів за це дадуть більше.
- **Клейноди** нараховуються так: `regalia = floor(10 × sqrt(villageLifetimeDucats / (village.scale × regaliaBase)))`. Поріг відносний до масштабу краю, тож множник ×1000 між краями не роздуває клейноди.
- **Родове дерево:** постійні бонуси за Клейноди: +% до всього доходу, стартові дукати, автопокупка найдешевшої будівлі, +1 год офлайн-ліміту, +1 слот походу. Ціни вузлів — у `src/content/legacy-tree.ts`.
- Завершене селище переходить у «Землі роду». **Данина** — не дукати (після ×1000 вони були б нулем), а **+2% до доходу всіх наступних країв за кожну завершену землю** плюс **слава щогодини** (`tributeGlory/год` з контенту, ліміт накопичення 24 год). Землю можна відкрити в режимі перегляду.
- **Переносяться:** слава, культура, герої, реліквії, писанки, клейноди, військо (кількість загонів; ліміт харчу нового краю діє лише на новий найм).
- **Обнуляються:** дукати, господарські будівлі й будівлі Січі.

### 3.7 Краї — шлях Війська Запорозького

### 3.8 Офлайн-прогрес
- **Базовий ліміт** 8 год. Його збільшують культура (Вечорниці), герой Знахарка, Родове дерево і особливість Великого Лугу. Стеля — 24 год.
- **Одна функція часу для онлайну й офлайну:** `advance(state, now) → { state, events }` (`src/core/advance.ts`; окремого `dt` немає — час рахується лише від `state.time.lastSeen`). Вона **аналітична й кусково-лінійна** за детермінованим розкладом подій, без ліміту й без покрокового циклу:
  ```
  точки розриву = зміни вітру (M1); далі — кінці бустів, повернення походів, погода, рівень води,
                  ціна солі, сіті й замовлення у (lastSeen, now]
  для кожного відрізка: ducats += farmIncomeRate(мод. на початку відрізка) × тривалість
                        glory  += gloryRate × тривалість;  stormsSurvived += бурі, що почалися в ньому
  ```
  `now ≤ lastSeen` або нескінченний `now` → стан без змін. Ставки рахуються в `number`, підсумки — у `Big`.
- **Хто викликає `advance`** (`src/core/offline.ts`):
  | Функція | Коли | Що робить |
  |---|---|---|
  | `tick(state, now)` | кожен тік циклу 10 Гц і перед кожною дією (store) | розрив ≤ `onlineGapSec` (5 с) → `advance`; довший → `applyOffline` (довгий «онлайн»-розрив не обходить ліміти) |
  | `applyOffline(state, now)` | відсутність | спершу тихо зараховує незабраний звіт; далі `eff = min(now − lastSeen, offlineCapSec)` **до** виклику `advance(state, lastSeen + eff)`; дукати × `offlineMult` і слава (до комори, §3.4) лягають у `returnReport`; бурі зараховуються одразу; `lastSeen = now`. Відсутність < `returnMinSec` (60 с) → без звіту, дохід одразу |
  | `resume(state, now)` | перший тік після повернення сторінки або після завантаження збереження | як `tick`, але годинник позаду `lastSeen` більше ніж на `onlineGapSec` → `applyOffline` зі звітом `clockBack`. **Лише цей шлях** повідомляє про годинник назад; тіки 10 Гц мовчать |
  Тест еквівалентності (§12.1: 8 год одним викликом проти 288 000 тиків по 0.1 с, < 0.1 %) тримається за побудовою; для слави — у межах комори, для дукатів — у межах `offlineCapSec`.
- Вітер, погода, рівень води й ціна солі — **чисті функції `(seed, часове вікно)`**, без збереженого стану, що змінюється в часі.
- Таймери походів і подій прив'язані до абсолютних часових міток, тому завершуються самі.
- **Походи й офлайн (M3, ADR 012):** `returnAt ∈ (lastSeen, now]` — точка розриву `advance` (перехід слота й `RaidReturned`, інтеграл доходу той самий). `applyOffline` інтегрує дохід до `lastSeen + eff`, а походи завершує до **реального** `now`: таймери походів офлайн-ліміту не мають. Тіки 0.1 с = один `advance` = `applyOffline` (та сама подія, той самий слот). Годинник назад нічого не повертає й не скасовує; стрибок уперед (`forwardJump`) завершує походи — прийнято (Q8), як день справ §3.9. `RaidReturned` може прийти з часу; `RaidClaimed` / `RelicFound` — лише з дії.
- **Захист від підкрутки годинника:**
  - якщо `now < lastSeen`, офлайн-нагорода дорівнює 0, а `lastSeen` **не зсувається назад** (інакше «годинник назад → вперед» давав би ліміт щоразу; ADR 002, поправка 3). Поки годинник позаду `lastSeen`, дохід не йде; вікно повернення пояснює це («годинник перевели назад»);
  - зберігається `time.maxSeen`: `now > maxSeen + forwardJumpCapSec` (7 д) рахується рівно як ліміт (`forwardJump`);
  - пізніше можна додати опціональну перевірку серверного часу.
- **Звіт повернення** (`ReturnReport` у `src/core/state.ts`, поле `returnReport` стану, зберігається):
  `{ awaySec, countedSec, capped, reason: 'normal'|'clockBack'|'forwardJump', ducats: Big, glory: Big }` (`countedSec ≤ awaySec`, `≤` стелі офлайну).
  Валюти чекають дії `claimReturn` (подія `ReturnClaimed`) — місце для подвоєння M8 (`claimReturn({ double })` після `rewarded`) без перерахунку. **Незабраний звіт** при наступній відсутності зараховується тихо (`creditReport`): нічого не губиться, нове вікно показує лише нову відсутність.
- **Вікно повернення** (M1: `ui/components/ReturnModal.tsx`): «Час відсутності: 3 години 21 хвилина» (`formatDuration`: дві найбільші одиниці з плюралами), «Зараховано: 8 годин (ліміт досягнуто).», дукати/слава, «Забрати»; `clockBack` → «нічого не нараховано»; без будівель — пояснення замість «+0». Показується, якщо `returnReport ≠ null`; HUD і панель `inert`, поки вікно відкрите. M3: рядок «Походи: N повернулося (регіони) — скрині на майдані» з `raidSlotsView` (`ReturnReport` не змінюється; здобич — лише через «Забрати» на слоті); парад загону — лише коли повернення сталося на очах (Q14). Далі — «▶ Подвоїти» (M8).

### 3.9 Мета-системи
- **Щоденний календар:** цикл 7 днів, на 7-й день сундук із писанками. Пропуск дня не скидає прогрес, він просто стоїть.
- **Завдання** (ланцюжок, щоденні, тижневі, повторювані) — §3.10.
- **Досягнення:** 50+ штук з нагородами в писанках.
- **Сезонні події** за реальним календарем:

  | Подія | Коли | Що змінюється |
  |---|---|---|
  | Коляда | грудень–січень | сніг, колядники ходять селом, ×2 писанок |
  | Великдень | весна | писанкові завдання |
  | Івана Купала | липень | вогнища, вінки на воді, нічні бонуси |
  | Покрова | 14 жовтня, козацьке свято | ×2 слави, парад війська |

  Події — це конфіг із датами, візуальним оверлеєм, завданнями і косметикою.
  Великдень — рухома дата, потрібна чиста функція обчислення (який пасхальний календар брати, перевірити при реалізації M6). Дати Коляди звірити з новим церковним календарем (Різдво 25 грудня з 2023 року).
- **Вісті дня, мандрівники, товар дня, погода в економіці** — §2.6.
- **«День»** для щоденних нагород і лімітів реклами рахується від монотонного `maxSeen` у локальному часовому поясі, тож перевод годинника назад не дає нового дня. Політика годинника (поруч із §3.8, M2-23): день монотонний (`max(збережений, поточний)`, зсув поясу на захід його не повертає); перевод назад не дає нічого; перевод **вперед** дає новий день справ — прийнято, бо справи платять лише м'яку валюту (хвилини доходу/слави) й ніколи писанки. Пояс (`settings.tzOffsetMin`, хвилини) пише платформа при старті; він є в збереженні й, отже, в експорті.
- **Локальні сповіщення** (тільки якщо гравець дозволив, не частіше 2 на день): «Козаки повернулися з походу», «Комора майже повна», «Щоденна нагорода чекає». M3 готує гачок: чистий селектор `raidAlerts(state)` (повернення в межах 30 хв зливаються в одне) + mock `NotificationService`; запит дозволу — після першого поверненого походу, не на старті, тихі години 22:00–08:00 (план M3 Q18 — відкрито, дефолт), увімкнення — M6.

### 3.10 Завдання (завжди є що робити)
Чотири види; панель завдань ніколи не порожня. Нагороди малі й у масштабно-незалежних одиницях (хвилини доходу / слави, писанки) — спільний тип `Reward` з віхами (§2.5).

| Вид | Як працює | Нагорода | Етап |
|---|---|---|---|
| **Наказ кошового** (ланцюжок) | 1 активне завдання краю в порядку календаря §2.4: «Збудуй пасіку», «Найми 3 козаків», «Підніми вітряк до 25». Ручний список ~25–40 на край; коли він скінчився — генеровані «підніми найближчу будівлю до наступної віхи». Деякі кроки запускають віху (§2.5). Кроки йдуть з відстанню: ціль потребує гри, дешеві «рівень 1» (вітряк, гончар, Майдан) — за цілями 10/25 (M2-27) | 5–15 хв доходу **або** 3–5 хв слави, інколи 2–5 писанок. Перші кроки хутора (поле 1, город 1, поле 10, пасіка 1) і кроки Січі платять славою: оплачені доходом, вони купували наступний крок одразу й проганяли ланцюжок за S1 (власник, 2026-11-22; M2-27) | **M2** (разом із віхами) |
| Щоденні | 3 з пулу за `hash32(seed, day)`, вагою під наявні системи («Купи 50 рівнів», «Заверши 2 походи», «Злови лелеку»); 1 перекрут за рекламу, 2 за писанки | 2 писанки кожне + 2 за всі три; слава | M6 |
| Тижневі | 3 більші за `hash32(seed, week)` («Пережий 5 бур», «20 тірів», «10 походів») | скриня: 30 писанок + 60 хв доходу | M6 |
| **Господарські справи** (повторювані) | завжди доступні фермерські: «Збери 1 год доходу тапами», «Купи 25 рівнів», «Відправ похід»; після виконання одразу нове | 3–10 хв доходу; **≤ 10 нагород на день**, далі лише лічильник | **M2** |

- **Зв'язок із календарем:** ланцюжок — це календар §2.4 у вигляді підказок «що далі»; онбординг §10 = перші 5 кроків ланцюжка.
- **Дані** `src/content/quests.ts`:
  ```ts
  interface QuestDef { id: QuestId; kind: 'chain' | 'daily' | 'weekly' | 'chore'; land?: VillageId; order?: number;
    goal: QuestGoal; reward: Reward; requires?: SystemId /* лише коли система є у збірці */; titleKey: string }
  type QuestGoal = { kind: 'building' | 'sich'; id; level } | { kind: 'count'; stat: StatId; n } // stat: levelsBought, hires, raidsDone, storks, storms, tapIncomeSec…
  ```
- **Стан (M2, save v3, §9.3):** `quests: { chain: listed { index, base } | generated { goal } | done, chores: { day, n, active, base, claims } }` — край ланцюжка береться з `village.id`; M6 додасть `daily: { day, ids, base, claimed, rerolls }` і `weekly: { week, ids, base, claimed }` (ще один bump). Лічильники — з `stats` (монотонні), `base` — значення на старті завдання; виконання **похідне** (не зберігається). Рівні й лічильники рухають лише дії, тож `QuestCompleted` приходить з дії (крок, уже виконаний при активації, — одразу); офлайн нічого не пропускає. Наступна справа — `hash32(hash32(seed, salt), n)` серед доступних (`requires`), без попередньої; ids і порядок кроків/справ заморожені (лише дописувати).
- Події: `QuestCompleted { id, kind }`, `QuestClaimed`. i18n: `quest.<id>.title`, параметри через плюрали.

## 4. Монетизація

> v1.3 (ADR 010, частково замінює ADR 006): гра заробляє на **rewarded-рекламі за вибором гравця** і **магазині** (преміум-валюта, «Без реклами», косметика, зручність). Банерів, interstitial і paywall як не було, так і нема.

**Принципи (стовп «Чесна монетизація», §1):**
1. Увесь контент (8 країв, механіки, герої, культура, віхи) — безкоштовний. Гру **можна повністю пройти без реклами й без грошей**; реклама й покупки лише пришвидшують і прикрашають.
2. Реклама тільки rewarded і тільки за натисканням гравця. Без примусових показів, без «реклами після N дій».
3. Гроші купують **час і красу, не силу понад межу:** ефект реклами на час Розквіту ≤ ~1.5×, ефект платника (усе куплене) ≤ ~1.75× (§2.3, §12.3).
4. Без лутбоксів і платних випадкових предметів; без таймерів-тиску («лише 2 години!») і FOMO-пропозицій, що згорають; ціни — з Google Play, локалізовані.
5. Усі ліміти — у ядрі (`src/core`), числа — у `src/content/monetization.ts`.

### 4.1 Преміум-валюта: писанки
**Рішення (рекомендація; питання власнику §17):** одна преміум-валюта — **писанки** (`pysanky`, уже в §3.1), яку і заробляють у грі, і купують у магазині. Причини: одна валюта = простіший UI й баланс (як «самоцвіти» в більшості idle-ігор); безкоштовний гравець має той самий доступ до кожного стоку, лише повільніше; писанки вже мають джерела й стоки в SPEC. Подача з повагою (§16): у магазині — «кошики писанок», факт-тултіп про писанкарство.

| Джерело (безкоштовно) | Писанок | ≈ на день |
|---|---|---|
| Щоденний календар (цикл 7 днів: 3·3·5·5·8·8·20) | 52 / тиждень | 7 |
| Щоденні завдання (3 × 2) + бонус «усі три» 2 | 8 / день | 8 |
| Тижневі завдання (§3.10) | 30 / тиждень | 4 |
| Лелека (частина ловів), вісті дня, віхи (§2.5), рідкісна здобич походів | — | 2–4 |
| Досягнення (50+, разові 5–25) | ≈ 600 за v1 | — |
| **Разом без реклами** | | **≈ 20 / день** (≈ 600 / міс.) |
| Реклама: «Дарунок» (§4.3) 3 × 5 | | + 15 / день |

Якір ціни: **100 писанок ≈ $0.99**. Безкоштовний гравець за місяць заробляє ≈ 600 (≈ $6 вартості).

### 4.3 Rewarded-реклама: місця
Спільні правила: кнопка «▶» показується лише коли реклама завантажена; **денний ліміт усіх переглядів 25**; між переглядами ≥ 30 с; «день» — §3.9; ліміти й нагороди рахує ядро; власник «Без реклами» отримує те саме без перегляду.

| Місце | Нагорода | Ліміт / кулдаун | Етап |
|---|---|---|---|
| Вікно повернення | ×2 офлайн-дохід | 1 на повернення; лише якщо відсутність ≥ 15 хв | M8 |
| Ярмарковий день | ×2 доходу на 30 хв, накопичується до 4 год | 8 на добу | M8 |
| Похід: прискорення | −50 % залишку | 2 на похід | M8 |
| Похід: здобич | ×2 | 1 на похід | M8 |
| Лелека | 10 хв доходу замість 60 с | лише на сам лелеку | M8 |
| Щоденні завдання | перекрутити одне | 1 на добу | M8 |
| Щоденний календар | ×2 нагорода дня | 1 на добу | M8 |
| **Дарунок** (у магазині, «безкоштовно») | 5 писанок | 3 на добу, кулдаун 2 год | M8 |
| Вісті дня | ×2 нагорода обраної відповіді | 1 на добу | M8 (після M6) |
| Мандрівник | ×2 тривалість бафу | 1 на мандрівника | M8 (після M6) |
| Тижневі завдання | ×2 скриня тижня | 1 на тиждень | M8 |

Не робимо: рекламу для культури й героїв (вони без таймерів), рекламу за «відновлення» після невдачі, рекламу як умову онбордингу.
- **SDK:** AdMob rewarded через `@capacitor-community/admob` (версію перевірити в M8). Згода Google UMP до першого запиту реклами; аналітика поважає згоду (consent mode).
- **Аудиторія:** не для дітей (Families policy не застосовується); IARC: шинок (згадка алкоголю), абстрактні походи, **внутрішньоігрові покупки**.
- `AdsService` (§9.4): `AdMobAds`, `MockAds` у вебі й dev. Нагорода — **тільки** після колбеку `rewarded` або за активним правом `noAds`. Реклама не завантажилась → «Реклама недоступна, спробуй пізніше», нагороди немає.

### 4.4 Покупки: техніка (деталі — §9.4, ADR 010)
- **Google Play Billing** через Capacitor-плагін. Кандидати (перевірено 2026-11-19, звірити в M8): `cordova-plugin-purchase` / `capacitor-plugin-cdv-purchase` (MIT, Play Billing 8.3, consumable / non-consumable / підписки, restore, опційний валідатор) — **рекомендовано**; Capawesome Purchases (Insiders, платна ліцензія, PBL 8.2); RevenueCat (свій бекенд, 1 % понад $2.5K MTR). Play вимагає PBL 8 для нових апок/оновлень до 31.08.2027 (PBL 7 — до 31.08.2026).
- **Видача:** стан `PURCHASED` (не `PENDING`) → дія ядра `grantPurchase { productId, tokenHash, purchaseTime }` → збереження на диск → лише тоді consume / acknowledge (Play повертає гроші за непідтверджене за 3 дні — звірити). Ідемпотентно: `tokenHash` у `purchases.granted`.
- **Перевірка в v1 — на пристрої** (рекомендація; питання власнику): підпис покупки Play перевіряється публічним ключем застосунку; гра офлайн і одиночна, тож злам шкодить лише виручці, не іншим гравцям. Мінімальний serverless-верифікатор (Play Developer API + RTDN для повернень) — після метрик (M10+).
- **Права не з сейва:** `noAds`, стартовий набір і косметика за гроші при кожному старті перевіряються запитом власних покупок у Play; у збереженні лише кеш для офлайну. Повернення коштів → право зникає при наступній перевірці. Імпорт збереження (§9.5) права не переносить. Повернення за consumable без сервера не відстежуємо (прийнятий ризик v1).
- **Офлайн:** купівля потребує мережі; куплене працює офлайн із кешу; «Відновити покупки» — у «Ще → Налаштування».
- Ціни показуємо лише з Play (`formattedPrice`), ніколи не хардкодимо. У web-збірці — `MockStore`; демо на itch.io без покупок.

### 4.5 Онбординг монетизації
- Перша пропозиція реклами — не раніше другого вікна повернення; магазин видно з S1, але жодних спливних пропозицій до дня 2. Стартовий набір — одна ненав'язлива картка в магазині й одна згадка після першого Розквіту.

## 5. Арт-дирекція

Повний еталон стилю — **`docs/art/ART-BIBLE.md`** (палітра з HEX, матеріали, світло, словник козацької архітектури, референси). Тут лише рамки.

### 5.1 Загальне
- **Роздільна здатність:** логічна ширина **320–400 px** (ціль ~360) з **цілочисельним масштабом**: `scale = max(1, floor(screenWidthPx / 320))`, і якщо `screenWidthPx / scale > 400`, то `scale + 1` (ліміт 400 перемагає: 1280 → ×4 = 320); `logicalWidth = floor(screenWidthPx / scale)` (1080 → ×3 = 360, 1440 → ×4 = 360, 720 → ×2 = 360, 1170 → ×3 = 390). Висота динамічна.
- Світ рендериться в **low-res render target** логічного розміру й масштабується nearest. Фільтри працюють на логічній роздільності. Плавність камери забезпечує субпіксельний зсув лише на етапі апскейлу.
- Пікселі спрайтів завжди цілі: `roundPixels`, `NEAREST` scaleMode.
- **Вид:** бокова діорама з глибиною (3–4 ряди по Y на смузі землі), не top-down.
- **Розміри спрайтів (детальний піксель):**
  - селянки 16×24 (селянин — на тілі козака 18×28), діти 12×16; полотна людей ширші (32 px) під знаряддя й рушниці;
  - козаки 18×28, кошовий отаман 20×30;
  - вершник з конем 36×32;
  - господарські будівлі 64×64 … 128×112 (хата тір I — полотно 76×56 з місцем під тінь); курінь 112×56; церква з банями 96×152; вежа 32×88; брама 80×112; секція частоколу 16×40 (тайлиться); вітряк 56×96 + крила 72×72;
  - іконки UI 16×16; портрети героїв 48×48.
  - Точні полотна й кадри всіх збудованих спрайтів — ART-BIBLE §2 (v1, M-ART).
- **Лінія:** темний **кольоровий** контур (не `#000`), на освітленому боці контур світліший (selective outline). Світло падає зверху-зліва. Шейдинг рампами зі зсувом тону, з фактурою матеріалів (очерет, глина, дошки, колоди, ґонт, камінь). Без «подушкового» шейдингу.

### 5.2 Палітра
- **Майстер-палітра 88 кольорів у 14 рампах** по 4–8 відтінків (`assets-src/palettes/master.json`, свотч `docs/art/palette.png`), зі зсувом тону: тіні холодніші й фіолетовіші, світло тепліше. Точні HEX — в ART-BIBLE.
- Кожен край додає 4–6 власних кольорів: Великий Луг — очерет і мул, Базавлук — морська бірюза, Степ — вохра й полин, Нова Січ — смола й темне дерево.
- **Час доби — LUT-грейдинг** (6 ключових кадрів: світанок, ранок, день, «золота година», сутінки, ніч) з інтерполяцією. Вночі світяться **emissive-маски** (вікна, кузня, вогнища, ліхтарі) поверх грейдингу. Окремих нічних спрайтів немає.
- **Бюджет кольорів на спрайт** (ART-BIBLE §4): проп/тайл/рослина ~16 кольорів із 3–4 рамп; будівля й людина ~24 із ≤ 6 рамп.

### 5.3 Шрифт
- **UI:** **Press Start 2P** (OFL, `src/ui/fonts/`, `docs/art/LICENSES.md`; власник 2026-11-18: у Pixelify Sans немає «І О П ʼ»). Кожен новий рядок перевіряй на «і ї є ґ ʼ»; гліфів ⚙ і − (U+2212) у шрифті немає.
- **Розміри — у цілих device px на піксель шрифту** (`uiScale` у `src/ui/theme.ts`; 8 font px = 1 em): `--font-s` = ⌈scale × 1.25⌉, `--font-m` = ⌈scale × 2⌉ device px на font px (і щонайменше на 1 більше за `s`). На 390@3 (×3) це ≈ 10.67 і 16 CSS px. **Відхилення від колишнього правила «8/16/24 логічних px»:** кратність логічному px дала б розмитий або завеликий шрифт; чіткість важливіша (M1-17).
- Числа моноширинні (tabular), щоб лічильник не «скакав».

### 5.4 Звідки береться арт (рішення: увесь арт робить Claude Code, ADR 004)
Прототип вийшов простим, бо спрайти малювались «наосліп» текстовими масками. Новий пайплайн побудовано так, щоб **кожен спрайт перевірявся очима**:
1. **Процедурні генератори** (`assets-src/gen/**/*.ts`) для будівель, рельєфу, дерев, тинів, частоколу, води й хмар. Генератор будує форму з примітивів матеріалів (стіна-мазанка, очеретяний дах, зруб, ґонт, дошки, вал) і проганяє проходи: **освітлення зверху-зліва → фактура матеріалу → AO в кутах → дизеринг переходів → кольоровий контур → selective outline → квантування в палітру**. Варіації (тіри, краї, сезони) — параметри, а не нові малюнки.
2. **Ручні індексовані маски** лише для дрібних, «авторських» речей: обличчя, кисті рук, деталі одягу, іконки, портрети. Персонажі збираються як **paper-doll**: тіло + шари одягу + палітрові свопи + анімація зсувами кінцівок. Після M-ART маски персонажів — ASCII-маски в самих генераторах (`assets-src/gen/lib/doll.ts`); окремі `assets-src/px/*.px` лишаються опцією для іконок.
3. **Атмосфера** (§6.3) — у коді рендеру, не в спрайтах. Виняток — анімація, що мусить лишатися на піксельній сітці: нахил рослин, оберт крил, полум'я — це запечені кадри генератора цілими px, рендер лише обирає кадр (ADR 004, поправка 2026-11-17). Генератор пише індекси рамп (не RGB) і поряд із кадром видає маски `@emissive` (нічне світло) і `@shadow` (відкинута тінь); `pnpm sprites` відкидає піксель поза палітрою.
4. **Цикл якості:** `pnpm sprites` → `/art-review` (скриншоти 390×844, день/«золота година»/ніч) → `art-director` → правки. Спрайт без ✅ не йде в main.
5. Сторонні паки й AI-генерація **не використовуються** (не потрібні). Якщо колись знадобляться — лише з ліцензією й записом у `docs/art/LICENSES.md`.

На виході — той самий формат атласу (`atlas.png` + `atlas.json` у форматі Pixi Spritesheet); `.aseprite` лишається підтримуваним джерелом на майбутнє.

Кадр за замовчуванням: горизонт на 35 % вікна між HUD і половинною шторкою (ART-BIBLE §2). На 360×800 половина шторки обрізає другий рядок будівлі приблизно на рядок тексту — **прийнято як є** (власник 2026-11-23): видимий край другого рядка підказує, що список гортається (`SHEET.minHalfBodyPx`).
- Світ ширший за екран (край 1 — 1920 px ≈ 5 екранів: хутір → передмістя → Січ, §3.0; один неперервний світ, зони — x-проміжки, `?zone=` — позиція камери; ADR 011). Камера тягнеться пальцем з інерцією, pinch перемикає 2 рівні цілочисельного зуму (звичайний і ближчий = масштаб +1, миттєво, без твіну); на ближчому рівні один палець тягне по обох осях у межах звичайного кадру, а небо зсувається вниз рівно настільки, щоб сонце чи місяць лишались у кадрі (M2-03). Подвійний тап центрує камеру — але лише якщо за ним протягом вікна подвійного тапу не було третього: серія тапів (заробіток) камеру не рухає, кожен тап зараховується одразу (M2-02). Вибір таба «Хутір» або «Січ» плавно везе камеру до відповідної зони.

### 6.3 Час доби і погода
- **Цикл доби:** за реальним локальним часом гравця, LUT-грейдинг із 6 ключовими кадрами (світанок 05:30, ранок 07:00, день 13:00, «золота година» 19:30, сутінки 21:00, ніч 23:00; кожен тримається певний час, далі плавний перехід — ART-BIBLE §8.1). Висота сонця й місяця відповідає часу; **видиме сонце завжди в лівій частині неба** (і на світанку, і ввечері) — стилістичне правило, бо світло в спрайтах зверху-зліва.
- **Порядок рендеру (ADR 001):** небо, далекий і середній плани малюються на CPU палітровими кольорами неба поточного ключа й **не грейдуються** → грейдований контейнер (хмари, земля, будівлі, люди, передній план) з одним LUT, змішаним між двома ключами → проходи води → шар світла (серпанок/туман, промені, плями світла, світлячки, дощ; без грейду) → emissive після грейду.
- **Атмосферний стек** (кожен ефект має рівень якості low/med/high, усі вимикаються налаштуванням «менше руху» там, де є рух):
  | Ефект | Реалізація |
  |---|---|
  | **Промені сонця** | CPU-карта тіней від сонця крізь хмари й кручі (high — повна роздільність, med — ½), на low — віяло статичних адитивних променів, що гасне за хмарою; GodrayFilter відкинуто (ART-10). Лише низьке сонце (світанок, «золота година»). Пил ≤ 40, що мерехтить у променях |
  | Туман і серпанок | далекі плани тонуються в колір горизонту (повітряна перспектива); дизерована смуга серпанку над землею за часом доби; у тумані — щільний банк |
  | Тіні хмар | тайли з бінарною альфою, що пливуть по землі; сила за часом доби, лише за прямого сонця |
  | Вода | власне дзеркало сцени рядками 1 px зі зсувами на цілі px (без розмиття), відблиски й доріжка сонця/місяця; брижі від дощу; брижі й піна біля човнів (M2-11) |
  | Вітер | запечені кадри нахилу трави, очерету, крон (цілі px), кадр обирається від сили вітру; крила вітряка — кадри зі швидкістю від вітру; корогви й прапорці — 4 кадри від вітру, у бурю 4 довші (`gale`); дим зноситься й сплющується вітром (M2-11); сила вітру = механіка краю 1 |
  | Світло вогню | **альфа-змішані** (не адитивні) теплі плями, що мерехтять (вогнища, горн кузні, смолоскипи вартових); перед вікнами — півеліпс світла від стіни (M2-29); м'які тіні від персонажів біля вогню — не зроблено (відкладено, M9) |
  | Місячне світло | уночі й у сутінки при ясному небі — 1-px холодний обідок верхніх країв пропів з боку місяця (M2-29, ART-BIBLE §8.3) |
- **Два годинники анімації:** рух людей (стан гри) іде за часом анімації завжди; атмосферний рух (хмари, вода, крила, рослини, вогонь, дощ, зорі) — за окремим «атмосферним» часом, який «менше руху» зупиняє (статичний кадр), а частинки вимикає. Люди під «менше руху» ходять.
- **Тіри якості:** `low/med/high` масштабують промені, пил, іскри, світлячків, бризки, дальній шар дощу, тіні хмар (ART-BIBLE §8.7). Без явного вибору гра стартує на `med` і один раз обирає тір за середнім fps перших секунд.
- **Ніч:** LUT робить сцену синьою й контрастною (а не просто темною); emissive-вікна, кузня, ліхтарі, вогнища на майдані Січі; зорі, місяць з доріжкою на воді, світлячки; селяни сидять на призьбах біля дверей хат, корчми й горна (вогнища для селян поза Січчю немає — нічний фокус = Січове вогнище, рішення M2-18), козаки — з люльками біля вогнищ майдану, вартові зі смолоскипами — на бойовому ході валу біля підніжжя веж (у галерею 28-px фігура не вміщається, рішення M2-19).
- **Сезони** за реальним місяцем: весна — цвіт вишень і лелеки; літо — соняшники й мальви; осінь — жовте листя, що падає, снопи; зима — сніг, що накопичується на дахах і частоколі, густіший дим, замерзла заводь.
- **Погода** — детерміновані події по 10–30 хв (функція `seed + час`):
  - дощ: сіре суцільне небо без сонця, місяця й зірок; струмені (дві плитки, що зсуваються цілими px, без шейдера й частинок) + бризки + мокра темніша земля + калюжі зі світлим краєм; окремий набір LUT під дощем (знебарвлений день, золота година без сонячної кривої) і м'якші відкинуті тіні (M2-29); уночі грейд м'якший, щоб силуети читались; після дощу іноді веселка (M6);
  - туман: світле сіре небо, щільний банк над землею, далекі плани тонуть; густий над плавнями (край 2) та вранці;
  - вітер: трава, очерет і корогви сильніше, дим зноситься;
  - гроза: спалах, що підсвічує сцену, звук, рідко;
  - сніг узимку.

### 6.5 Будівлі
- **Візуальні тіри** на віхах рівнів: хутір 1 / 10 / 25 / 50 / 75 / 100 (тіри I–VI, бо кожна віха §3.2 — новий тір), Січ 1 / 10 / 25 / 50 (I–IV). Рівень 0 = порожня ділянка. Кожен тір — це окремий спрайт: хата стає більшою, з'являються квіти, тин, рушник у вікні, стяг; на 100-му рівні золотий акцент і мерехтіння.
- **Ділянки** (`render/bridge.ts` `connectWorld` + core-селектор `visualTiers`; дані у `content/villages/khortytsia.layout.ts`): кожна будівля краю 1 — `TierSprite` (тір I + вигляд кожного наступного тіру: основа + додатки, або «як попередній»), `composeWorld` розгортає його в пропи з `plot { building, from, until }`; смуги ґрунту (вал, рів, майдан) міняють тайл за тіром. Тест `tests/unit/content/tiers.test.ts`: кожен тір I–VI / I–IV кожної будівлі має кадри. Косметичні варіанти — додатки з `plot.variant` за `plotVariant(seed, building)` (§2.6). **Порожня Січ = степовий табір**: без валів — степ замість валу, без куренів — трава з витоптаним місцем і дровами біля вогнища. Без гри (рендер окремо) стоїть усе; `?state=showcase` = кадр M-ART, `?state=tiers&tier=N` — усі будівлі на тірі N.
- **Ідл-анімація** кожної будівлі (2–8 кадрів у циклі): крила вітряка (швидкість ~ рівню і вітру), бджоли біля вуликів, вогонь і іскри в кузні, дим із димарів, прапорці на ярмарку.
- **Будівництво** (перша покупка):
  1. з'являються риштування;
  2. 2–3 селяни підходять і стукають молотками (3 стадії по 0.4 с), летить пил;
  3. «pop» зі squash & stretch;
  4. конфеті.
- **Підвищення тіру:** спалах, банер «Тір II», здіймається стяг, коротка фанфара.
- **Звичайне покращення:** легкий squash 1.0 → 1.08 → 1.0 за 120 мс, монетки летять від лічильника до будівлі.
- **Як збудовано в M2** (`render/fx/construction.ts`, `fx/build.ts`, числа `BUILD` у `render/atmosphere/config.ts`): на `BuildingUpgraded` / `SichUpgraded` 0 → 1 — риштування (`scaffold.s|l`; висока широка будівля — кілька `l` поруч, `scaffoldBays`) → 3 стадії по 0.4 с зі стуком на кожній (поки лише лічильник `stats.knocks`, звук — M7) → pop 1 → 1.08 → 1 за 180 мс цілими px (Q5, ART-BIBLE §2) → 24 конфеті ≤ 1.2 с; на `TierReached` — зірочка-спалах (уночі — теплий обідок на будівлі), стяг 3 с і DOM-банер «Тір II». Економіка не чекає анімації. «Менше руху»: стадії й банер лишаються, без pop, пилу, конфеті й спалаху. **M2-29 D (рішення власника 2026-11-23: будівельники приходять завжди):** будівельники — 2 (`scaffold.s`) / 3 (`scaffold.l`) найближчі **за маршрутом** чоловіки громади (`selianyn`), хоч би як далеко (і вночі — виходять із дверей), ідуть до риштування й б'ють молотком (`work-build`: удар на рівні грудей, без ковадла; жінки не будують — рішення art-director), кожен на своє місце `BUILDERS.slots`; риштування з'являється одразу, а перша стадія стоїть, поки не прийде перший із них, але не довше `BUILDERS.waitMaxS` 25 с (заміряно: хутір удень 2–25 с, передмістя з малою громадою до 44 с, уночі до 66 с — після межі стадії йдуть, а чоловіки однаково приходять); лише тоді 3 стадії зі стуком (до того — без стуку), удвічі повільніше, поки хтось б'є; потім вертаються до свого дня. Поки риштування стоїть, ніхто не працює на цій будівлі, а місця для розмов ближче `BUILDERS.clearPx` 16 px до будівельників закриті. Економіка не чекає: рівень уже куплено. Якщо в громаді немає жодного чоловіка (або до ділянки нема стежки) — стадії йдуть одразу; під `?freeze` — теж не чекають (`render/agents/sim.ts` `assignCrews`/`crewState`, числа `BUILDERS` у `content/agents.ts`). Січ — без постатей (селяни туди не заходять; козацький `work-build` — M9). Звичайне покращення (`BuildingUpgraded`/`SichUpgraded` з `from` ≥ 1, лише дія гравця): 3 монетки валюти покупки (дукати / слава) летять дугою Безьє від лічильника до будівлі, якщо її видно над шторкою (`WorldApp.buildingOnScreen`, чисте `render/screenMap.ts`), коли перша долітає — squash 1 → 1.08 → 1 за 120 мс цілими px (виняток Q5, як pop); числа `UPGRADE_JUICE` у `content/juice.ts`; «менше руху» — без монеток і squash. Фанфара — M7.

### 6.6 Життя селища (AI селян)
- Кількість селян залежить від сумарних рівнів будівель (від 3 до ~25 на екрані).
- **Граф стежок** (вузли + ребра) задається в даних краю. Рух відбувається по графу (A* або BFS по малому графу).
- **Скінченний автомат селянина:**
  ```
  Idle → GoTo(workplace) → Work(10–30s) → GoTo(random POI: колодязь, ярмарок, лавка)
       → Chat(якщо поруч інший селянин, 3–6с, бульбашки-іконки) → Idle …
  Ніч: GoTo(вогнище | хата) → Sit / Sleep
  ```
- **Ефект робітника:** якщо селянин працює в будівлі, над нею інколи вилітає «+N». Це суто візуально, економіка аналітична.
- **Козаки (живуть у Січі):**
  - тренуються на майдані строєм (drill), отаман стоїть перед строєм; вартові на вежах;
  - вільні козаки ходять у передмістя: шинок, кузня (точать шаблі), ярмарок; кобзар грає біля шинку;
  - на старті походу виходять із брами під малиновою корогвою на чолі з отаманом; при поверненні в'їжджають зі скринею здобичі, а селяни з передмістя підбігають і радіють;
  - вночі сидять біля вогнищ на майдані з люльками.
- **Зв'язок зон (видимий):** селяни возять вози з харчем до брами Січі (частота ~ харчу); на свята (Покрова, Купала, Коляда) козаки спускаються в хутір, і на майдані передмістя разом танцюють гопак, співають, палять вогнища.
- Селяни ніколи не заходять усередину Січі (історична деталь), лише до брами.
- **Як збудовано в M2** (косметика в рендері, `render/agents/`; граф і спавни — `content/villages/khortytsia.paths.ts`, розклад — `VILLAGER_DAY`, `COSSACK_DAY`, бюджети `AGENT_BUDGET`: селян 25, козаків 16, мандрівників 2, возів 3 на весь світ, Q11): BFS по графу з доступом за роллю (усі вузли Січі, крім `sich.gate`, — лише для козаків; юніт-тест); пул детермінований (такти 60 Гц, mulberry32 на агента з `seed`, пози = f(seed, тактів)), без алокацій на такт. Селяни: робочі години 06:00–21:00, idle → walk → work 10–30 с → walk → talk 3–6 с; працюють лише там, де будівля стоїть (тір ≥ 1); уночі — свої місця біля дверей (≤ 2 з одного боку) або в хаті. Склад — 25 авторських спавнів громади (11 перших + 14 «поселенців» M2-29 D: двоє на нових робочих місцях — грядка городу, другий вулик, — решта ходить між місцями балачок і на ніч іде в хату чи шинок); на сцені перші `populationView(state).villagers` за порядком: 3 + ⌊1.4·√Σрівнів⌋ (ферма + відкриті будівлі Січі), до 25 (`VILLAGER_GROWTH`): 4 на першому рівні, ≥ 8 з усіма будівлями на тірі I, 25 від Σ ≈ 250; новий виходить із дверей хати, зайвий іде в хату й зникає (як козаки). «+N» — замінено відблиском `glint` над місцем роботи, без чисел і без зв'язку з економікою (рішення M2-18); бульбашки балачки — M9. Козаки: на сцені min(піхота, 16) (`populationView`), стрій на майдані з отаманом (слово → «Слава» → муштра → вільно), огляд строю раз на цикл; вільні — у шинку, кузні, на ярмарку; уночі люльки біля вогнищ або курінь; найнятий виходить із дверей куреня (`CossackHired`), втрачений іде до куреня й зникає. Вози — §3.0. Мандрівники — розклад слотів у core (`visitorAt`, §2.6), лише вдень, у Січ ніколи. Вихід загону з брами — M3; свята з гопаком — M6.

### 6.7 UI-джус

- Червоні крапки на табах: є нагорода за завдання (на «Ще», лише при згорнутій шторці — M2-25), похід завершено, нова культура доступна, Розквіт досягнуто.

- Камера трясеться на 2 px протягом 150 мс тільки на великих подіях. Ефект вимикається налаштуванням «менше руху».

## 7. Аудіо

### 7.1 Музика
- Кожен край має власну петлю на 90–180 с, без вокалу. Звучання — **«теплі народні інструменти»**, а не чіптюн, щоб пасувати до атмосферного арту. Легка «піксельна» стилізація (обмежена поліфонія, трохи lo-fi) допустима.

| Край | Характер | Інструменти |
|---|---|---|
| Хортиця | дорійський лад, спокійно, простір над Дніпром | бандура, сопілка, дрон |
| Великий Луг | тиха, водяна, мерехтлива | цимбали, сопілка, очеретяна флейта |
| Базавлук | морська, широка, хвилі | бандура, бубон, низький дрон |
| Чигирин | урочиста, міська | ліра, скрипка, бубон |
| Чортомлик | похідна, енергійна | довбиш (литаври), сурма, бандура |
| Слобожанщина | кінний ритм, лісостеп | скрипка, бубон, кобза |
| Чумацький шлях | ліричний мінор, довгі ноти, степ | ліра, сопілка |
| Нова Січ | розлога, гідна, фінальна | повний троїстий склад |
| Ніч | приглушена варіація теми краю | ті самі, тихіше, з реверберацією |
| Свята | колядкові, купальські, покровські мотиви | — |

- Аранжуємо народні мелодії (public domain) або пишемо оригінальні. Не використовуємо сучасні записи чи аранжування інших авторів. Джерела мелодій — у `docs/content-sources.md`.
- **Реалізація (рішення, ADR 005):** уся музика генерується кодом. Пісні описуються даними у трекерному форматі (`src/audio/songs/*.ts`), а звук синтезується на Web Audio **фізичним моделюванням**: Karplus–Strong для щипкових (бандура, кобза, цимбали), шум + синус з вібрато для сопілки, пилка з фільтром для трембіти й сурми, шум + синус для бубона й литавр. Згенерована реверберація (convolution з алгоритмічним імпульсом).
- Щоб берегти батарею, треки можна **попередньо відрендерити** через `OfflineAudioContext` у `pnpm music` (OGG + M4A для iOS) і грати як файли. Вибір режиму — при реалізації M7 за вимірами CPU.
- Кросфейд 1.5 с при зміні краю, доби чи свята.

### 7.2 Ембієнт (окремі шари)
Вода, вітер в очереті, птахи вдень, жаби й цвіркуни вночі, дощ, далекий гомін Січі (брязкіт, сміх), тріск вогнища. Звуки синтезуються кодом (шум + фільтри + гранулярні патерни). Гучність залежить від того, що видно в камері.

### 7.3 SFX

### 9.2 Потік даних
```
 UI (React) ──dispatch(action)──▶ GameStore (core) ──emit(events)──▶ Render bridge (Pixi)
     ▲                              │  tick(now) 10 Гц                 │ анімації, частинки
     └────── useSyncExternalStore ◀─┘                                  └ AudioManager (sfx)
```
- **Логіка** працює з фіксованим кроком **10 Гц** (`setInterval` / акумулятор у rAF).
- **Рендер** іде через rAF: 30 fps за замовчуванням (селище живе й так), 60 fps під час взаємодії, драгу камери й джусу; налаштування «економія батареї» фіксує 30.
- Store генерує доменні події (`BuildingUpgraded`, `TierReached`, `RaidReturned`, `StorkSpawned`…). Render і Audio підписуються на них і **ніколи не змінюють стан напряму**.
- **Store (M1, `src/core/store.ts`):** `getState` (стабільний знімок між змінами), `dispatch(action, now)`, `tick(now)`, `resume(now)`, `replace(state)` (→ `StateReplaced`), `subscribe`, `onEvent`. **Кожна зміна спершу йде через `tick`**, тож дія після довгої відсутності рахує її через `applyOffline` з лімітами. Події M1: `WindChanged`, `BuildingUpgraded`, `SichUpgraded`, `TierReached`, `CossackHired`, `Tapped`, `ActionRejected`, `OfflineApplied`, `ReturnClaimed`, `StateReplaced`; M2: `StoryBeatReached { id, granted }`, `QuestCompleted { kind, id }` (лише від дій), `QuestClaimed { kind, id, granted | null }`; M3 (ADR 012): `RaidStarted { slot, region, tier, returnAt }` (з дії), `RaidReturned { slot, region, success }` (з часу: тік, офлайн, завантаження), `RaidClaimed { slot, success, granted, relic }` і `RelicFound { id }` (лише з дії). Рендер грає парад лише на `RaidReturned`, що прийшов наживо, не з `applyOffline`/`StateReplaced`. Час сам рівнів не змінює, тож `TierReached`/`QuestCompleted` ніколи не приходять із завантаження чи офлайну. Відмова дії = стан без змін + `ActionRejected { action, reason }`, ніколи не виняток.
- **Шлях читання:** UI й рендер читають стан лише через `core/selectors.ts` і події. Рендер (`render/bridge.ts`) не імпортує `core/{actions,advance,offline,store}` (ESLint `imports[render-actions]`, типи дозволено); годинник і цикл 10 Гц — у `src/platform/loop.ts` / `lifecycle.ts` (прихована сторінка = відсутність).

### 9.5 Збереження
- **Формат:** JSON-конверт `{version, seq, checksum, payload}` (`src/core/save/serialize.ts`): `payload` — рядок JSON стану (Big → рядок), `checksum` = FNV-1a 32 над UTF-8 `payload` (помітити пошкодження, а не античіт), `seq` — номер запису (розв'язує нічию за `lastSeen`). Розбір ніколи не кидає: розмір ≤ `SAVE.maxChars` (256 K символів) → JSON → **новіша версія першою** (і в конверті, і в payload) → рівно чотири ключі → checksum → міграції → `validateState`.
- **Вибір при старті** (`core/save/load.ts` `chooseSave`, `platform/saves.ts` `bootGame`; завантаження — до React, у `main.tsx` → `ui/game.ts`), далі перший тік — `resume` (§3.8):
  | Слоти | Результат | Повідомлення |
  |---|---|---|
  | обидва читаються | пізніший за `lastSeen`, нічия — більший `seq` | — |
  | один пошкоджений | інший | «відновлено» |
  | обидва пошкоджені | нова гра; пошкоджені копії → `ck.save_damaged_a/b` | «пошкоджено» |
  | новіша версія або завеликий слот у будь-якому | нова гра в пам'яті, **запис вимкнено** | «онови гру» |
  | сховище не читається | нова гра, **запис вимкнено** | «недоступне» |
- **Запис:** дві копії `ck.save_a` / `ck.save_b` по черзі; saver завжди пише в слот, який **не** щойно завантажений/записаний, — найновіша добра копія ніколи не та, що перезаписується. Збій запису не валить гру (наступний запис пробує знову).
- **Автозбереження** (`platform/autosave.ts`): кожні 10 с, одразу після `TierReached` / `CossackHired` / `ReturnClaimed`, на паузі сторінки (`visibilitychange: hidden`, `pagehide` — `lifecycle.ts` `onPause`) і при демонтажі. M3: одразу після `RaidStarted` / `RaidClaimed`. Далі: переселення (M5), Capacitor `pause` (M9).
- **Одна вкладка:** Web Lock `cossack-kin-game` (`platform/singleTab.ts`); друга вкладка гру не запускає (`OtherTab`). Без Locks API гра йде.
- Debug-пресети `?state=` і `?freeze` грають у пам'яті й ніколи не чіпають `ck.save_a/b`.
- Міграції `vN → vN+1` для кожної зміни схеми, кожна з тестом; ланцюг (`save/migrations/index.ts`), дірка = помилка: v1 → v2 → v3 (таблиця §9.3) → v4 (M3-04: походи, реліквії; e2e reload зберігає похід у дорозі). Фікстура на кожну версію (`tests/fixtures/saves/v1.json`, `v2.json`, `v3.json` — зняті з гри бота, незмінні); e2e reload зберігає віхи й квести (M2-24).
- **Довіра до експорту (прийнято, M2-22):** checksum не захищає від підробки — відредагований і переписаний експорт завантажиться, якщо пройде `validateState`. Прийнятно: слава й дукати не мають грошової цінності й не пов'язані з рекламою чи покупками (права — лише з Play, §4.4). Відкрито до M8b: писанки теж лежать у `currencies` і продаються — їхній захист від редагованого експорту вирішити разом із магазином.
- **Експорт / імпорт** збереження рядком base64 у налаштуваннях, для перенесення й багрепортів. Імпорт обнуляє `purchases.entitlementCache` (права знову з Play, §4.4); куплене за писанки лишається.

### 9.6 Модифікатори
Усі бафи (культура, герої, реліквії, Родове дерево, особливість краю, бусти, свята) збираються в одну функцію `collectModifiers(state, now): Modifiers`. Структура: `{ incomeMult, costMult, gloryMult, raidTimeMult, lootMult, offlineCapSec, offlineMult, … }`.
Результат кешується, а кеш інвалідовується при зміні відповідних частин стану (у M1 кешу немає — тік ≈ 10 мкс, 24 год ≈ 0.7 мс; кеш — M4, лише якщо заміри покажуть потребу). M1-поля: `incomeMult` (оборона), `buildingMult` (вітер і «Вітряки ×2» на вітряку), `costMult`, `gloryMult`, `powerMult`, `offlineMult`, `offlineCapSec`, `gloryCapSec`. M3: `lootMult` (скарбниця, «Порохівниця»), `relicChanceMult`, `raidTimeMult` (1 до M4); «Пернач» — у `powerMult`. Реліквії й скарбниця діють лише через `collectModifiers`. Модифікатори множаться (мультиплікативно), формула кожного описана в контенті.

## 12. Якість

### 12.1 Тести (Vitest)
- `economy`: cost/prod на межових рівнях, віхи, модифікатори.
- **Еквівалентність офлайну:** `advance` 8 год одним викликом ≈ 288 000 тиків по 0.1 с (відхилення < 0.1 %, з вітром); адитивність a→b→c = a→c; `applyOffline` 3 год = `advance` 3 год (у межах лімітів).
- Античіт часу: годинник назад → 0 і `lastSeen` не спадає (цикл «назад → вперед» ×5 = 0); стрибок уперед → ліміт.
- Престиж: що лишається, що обнуляється, формула клейнодів.
- Міграції збережень: фікстури старих версій.
- Походи: таймери, шанс успіху з фіксованим seed; **той самий стан на старті → той самий результат** (перезавантаження, офлайн, порядок тіків); повернення тіками 0.1 с = одним `advance` = `applyOffline`; прев'ю картки = видана здобич; запобіжник реліквії; зміна дня не чіпає походи в дорозі (M3, ADR 012).

### 12.2 E2E (Playwright, 390×844)
- Новий гравець проходить онбординг до першого походу.
- Перезавантаження → вікно повернення з правильною сумою (час підмінено через fake clock).
- Скриншот-тести (`@screens`) головних екранів для кожного краю: світанок, день, «золота година», ніч; дощ; зона хутора й зона Січі.
- **Детермінованість:** debug-параметри URL `?seed=&time=&weather=&season=&zone=&freeze` (лише в dev/test-збірці) заморожують анімації й час. Chromium запускається з увімкненим WebGL.

### 12.3 Балансова симуляція (`pnpm balance`, з'являється в M1)
- Бот грає «жадібно»: купує те, що найшвидше окупиться з урахуванням очікування на ціну — `(ціна − дукати) / дохід + ціна / Δдохід` за **сталим** доходом (без вітру моменту), і робить 2 сесії на день по 7 хв (тапи, походи, завдання). Кожне готове завдання забирає реальною дією `claimQuest` одразу (M2-27). До M2-27 бот рахував `Δincome / cost` за вітром моменту: у бурю відкладав на вітряк 13K замість поля за 10 і не купував нічого всю S1 — міряв простої, не гру (власник, 2026-11-22).
- **Профілі** `--profile free|ads|payer` (§2.3): free — без реклами й покупок; ads — кожне місце §4.3 на ліміті (те саме, що «Без реклами»); payer — ads + «Козацька казна» щомісяця + стартовий набір + кошик M на місяць, усі писанки йдуть у стоки зручності (слот, офлайн-години, «Попутний вітер» на ліміті). Межі — у `pacing.ts` (`profiles`). Профілі ads/payer з'являються в симуляторі в M8; до того звіт друкує `n/a`.
- **Важелі монетизації** (один за раз, `monetization.ts`): денний ліміт реклами й кожного місця, тривалість і множник Ярмаркового дня, ліміт «Попутного вітру» на день, ціни стоків, писанки «Казни» на день, джерела писанок free. Якщо payer > 1.75× — спершу ріжемо скіпи часу, не бонуси free.
- Звіт також: писанок зароблено / витрачено на день за джерелом і стоком, день першої косметики й 3-го слоту для free, відношення часу до Розквіту ads/free і payer/free.
- **Походи в боті (M3-08):** на старті сесії бот забирає повернені й запускає в кожен вільний слот пропозицію дошки з найбільшою очікуваною здобиччю (× шанс) за час до наступної сесії; першим походом — розвідку 5 хв одразу після першого козака. Звіт: походів на день, частка здобичі в дукатах (≈ 5–15 %, ціль — звіт, не гейт), % успіху, день кожної реліквії, писанок на день зі здобичі, дій походів за сесію (≤ 4, звіт).
- **Визначення метрик:**
  - **дія** — одне натискання кнопки покупки в будь-якому режимі (×1 / ×10 / ×25 / MAX), старт чи збір походу, покупка вузла культури (забирання завдання — не дія, рахується окремо). «Ще раз» на поверненому слоті = 2 дії (збір + старт); «Забрати все» (Q17) = по дії на кожен слот;
  - **S1 з походами:** стеля `s1MaxActions` = 40 лишається (лише звіт); походи додають ≈ 2–4 дії на сесію. Якщо S1 вийде понад 40 — спершу тюнінг, підняти стелю — лише рішенням власника (план M3 Q20);
  - **відчутна покупка** — новий тір будівлі, нова будівля, новий тір Січі або новий тип загону;
  - **новинка** — відчутна покупка (тір, перескочений одним натисканням, теж рахується), сюжетна віха, крок «Наказу кошового» (справи — ні), крок механіки, відкриття системи або краю (§2.4). Новинка, що сталася офлайн (буря, віха), зараховується сесії, у яку гравець її побачив. M3 додає види `firstRaid`, `firstRelic` (кожна нова реліквія), `raidTier` (перший старт тиру; ref = тир); календар §2.4: перший похід S1 (≤ 180 с), перша реліквія S2–S5, похід 4 год S6–S10. Звичайний похід і збір — не новинка.
- **Звіт** (markdown + CSV у `reports/balance/`):
  - журнал новинок (сесія, час, вид, id) і стрічка «сесія → новинки» для тижня 1;
  - `maxSessionsWithoutNovelty` (тиждень 1; і без кроків ланцюжка — лише звіт), новинок на день (тиждень 1), `maxDaysWithoutNovelty` (після тижня 1);
  - дій у S1 проти `s1MaxActions` (лише звіт; коридор 5–15 — медіана з S2) і забирань завдань за сесію;
  - час до кожного запису календаря §2.4 проти його вікна (`n/a`, якщо системи ще немає в збірці);
  - час до кожної віхи;
  - час до Розквіту кожного краю;
  - дій і відчутних покупок за сесію;
  - відчутних покупок за 8 год офлайну;
  - частка офлайн-доходу;
  - різниця часу до Розквіту з рекламою й без (≤ ~1.5×) і для платника (≤ ~1.75×).
- CI (`pnpm balance --check`, з M1-15) падає, якщо час до Розквіту краю виходить за цільовий коридор із розділу 2.3, якщо в тижні 1 сесій без новинки поспіль більше за `pacing.novelty.maxSessionsWithoutNovelty` (M1: 1, з M2: 0, §2.3) або якщо наявний запис календаря §2.4 виходить зі свого вікна. Дні 8–60 — лише у звіті (власник, 2026-11-19).
- Симулятор моделює кожну систему з етапу, де вона з'являється: перший похід < 3 хв — з M3; нагороди віх, кроки ланцюжка й справи (бот забирає все) — з M2; товар дня й погода — з M6. Стійкість перевіряти на `--seeds 1,…,12` (після M2-27 — 1 провал: seed 7, кузня S2); гейт CI — seed 1/2/3 і швидкість симулятора (60 днів ≤ 10 с CPU).

### 12.4 Продуктивність
- **Ціль:** стабільні 60 fps на Android середнього класу (Snapdragon 6xx / 4 ГБ RAM).
- Один атлас на край (≤ 2048²) + спільні атласи. Після M2: `khortytsia` (край: будівлі, ґрунт, пропи, fx будівництва; 2042×1274), `people` (селяни, козаки, вози, мандрівники — спільний для країв), `sky` (хмари й їхні тіні), `ui` (іконки для DOM). Pixi v8 батчить кілька текстур в одному виклику — змішування атласів у Y-контейнері не додає draw calls (замір M2-01).
- Ліміти (на весь світ, Q11 плану M2):
  - частинок ≤ 300 (заявки — найгірший випадок на весь світ);
  - селян ≤ 25, козаків у показі ≤ 16 (решта — лише в UI), мандрівників ≤ 2 пози, возів ≤ 3 (`AGENT_BUDGET`);
  - draw calls ≤ 30 (світові `@screens` M2 ≤ 14: +2 човни, +3 місячний обідок; +4 за кожну позначену будівлю).
- Замір M2 (M2-28, SwiftShader на ноутбуці, CPU ×4): render 11.5–24.3 мс/кадр, гарячих точок немає; замір fps на телефоні — відкрито (плани M2-28/M2-30).
- Холодний старт до інтерактиву ≤ 3 с.
- Розмір APK ≤ 40 МБ.

## 15. Реліз і стор
- **Google Play.** Акаунт розробника, політика конфіденційності (обов'язкова через рекламу, аналітику й покупки), анкета Data safety, рейтинг IARC. Експортований сейв містить зсув часового поясу пристрою (`settings.tzOffsetMin`, M2-23) — згадати в політиці конфіденційності.
- **Покупки (M8b, ADR 010):** платіжний профіль продавця й податкові дані в Play Console; товари й шаблони локальних цін (UAH, USD, EUR, PLN); ліцензовані тестувальники й тестові картки; closed testing із реальними покупками до продакшену; Play Billing Library ≥ 8 (дедлайн 31.08.2027; на момент релізу звірити); комісія Play (15 % на перший $1M/рік за програмою — звірити); віртуальна валюта лише через Play Billing (Payments policy); у сторінці стору — «Містить рекламу · Покупки в застосунку»; IARC — «внутрішньоігрові покупки», без випадкових предметів; Data safety — історія покупок (якщо йде в аналітику), рекламний ID (AdMob); власники «Без реклами» не ініціалізують рекламний SDK. Політика повернень і текст «Відновити покупки» в налаштуваннях.
- Для нових особистих акаунтів діє вимога **закритого тестування перед продакшеном**. Перевір актуальні умови в Play Console.

## 16. Культурні нотатки
- Козацькі стяги малинові (`#a3123a`) з золотими символами. Сучасну державну символіку в світ гри не вставляємо, хіба що окремою косметикою або подією з поясненням.
- Імена, приказки, пісні беремо з народної творчості (public domain). Тексти пісень сучасних авторів не використовуємо.
- Ремесла (вишивка, писанка, кераміка, бортництво) показуємо з повагою: короткий факт-тултіп при першому відкритті.
- **Без карикатурних стереотипів**, особливо щодо «ворогів» у походах. Ворог абстрактний: «фортеця», «табір», «розбійники».
- **Історична точність без важкості:** дати Січей подаємо як «близько …»; трагічні сторінки (руйнування Січей, Батурина) не робимо ігровими подіями. Короткі історичні довідки — у тултіпах країв і в глосарії.
- Устрій Січі відтворюємо з повагою до джерел: курені довкола майдану, церква Покрови, пушкарня, скарбниця; жінки й господарство — поза Січчю, у хуторах і передмісті.
